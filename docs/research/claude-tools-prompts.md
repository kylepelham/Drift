The [context report](claude-context.md) owns compaction, read-cache lifecycle and provider result budgets; the [execution report](claude-execution.md) owns scheduler, hooks and request retries. ## Priority findings

1. **Enforce filesystem correctness in tools, not prose.** Edit and Write ask for a prior read and check a per-session read record. Both re-read at execution, but their conflict check primarily depends on *newer* modification time; equal or older mtimes can bypass content comparison. The writer flushes a temporary file and renames it over the target, but falls back to a non-atomic direct write on failure. Neither branch compares content at replacement time. Add content-identity checks and a per-path mutation lock in Drift before presenting this as optimistic concurrency [129054200-129056300; 129063100-129065000; 121044857-121048300].
2. **Compile prompts for actual model/tool/platform capabilities.** Claude's system text is assembled from conditional sections, a cached environment section and the current tool catalog. Tool descriptions are constructed asynchronously per request. The `Bash` instruction still describes bash/zsh, Git Bash and `ls`; an opt-in Windows PowerShell tool has separate semantics. Copying the wording into a GPT/Gemini/Windows prompt would teach nonexistent affordances [126682000-126698000; 131602700; 131613955; 123778110; 129775528].
3. **Spend extra inference deliberately.** Normal file searches are local ripgrep/glob. Agent exploration, forked skills, optional notes, opt-in subagent summarization, auto-mode handoff classification and server-side advisor paths add requests or model work. Their presence does not show that they improve results or reduce latency. Instrument calls per job, not just the foreground response [128900000; 128911000; 127105703; 131613955; 127020268-127026406].
4. **Make search and output limits navigable.** Glob returns at most 100 by default, Grep defaults to filenames and paginates at 250 entries, shell has a separate persisted-output path, and the general result processor may replace oversized text with a preview. The model must receive a precise continuation or retrieval handle; otherwise truncation can look like a complete search [129074000-129080500; 129790000-129792500; 125237908-125241781].

## What builds the model request

**Observed.** `d2` constructs the normal system section list; `CLAUDE_CODE_SIMPLE` selects a drastically shorter identity/CWD/date prompt. Normal sections cover role, system/tool-result interpretation, task scope, risky actions, available-tool instructions, tone and output efficiency. It obtains environment, output style and tool-name set, then computes named dynamic sections via `W3K`. `W3K` memoizes sections unless `cacheBreak` is set; MCP instructions use the cache-break variant and include only connected servers with instructions. A global-cache boundary is conditional on a force variable or `tengu_system_prompt_global_cache`; the request builder later splits system blocks when permitted. The user-specified output style may suppress the coding-instructions section with `keepCodingInstructions === false` [126682000-126698000; 125405447; 131602700-131604000].

`JXK` provides primary working directory, worktree warning, git status, additional directories, platform/OS, current model ID and knowledge cutoff. It also advertises Claude-specific model family and fast-mode claims. This is a Claude product statement, not portable environment data. Tool names in `g7f` decide whether the instructions mention Todo, Agent, Skill and deferred-tool search, and whether they tell the model to use dedicated Read/Edit/Write/Glob/Grep rather than shell. Instructions to parallelize independent calls live here, but safe/unsafe scheduling lives in the runtime, as the execution report shows [126692000-126699000].

`eF8` turns each available tool's `prompt()` into its API description, converts its input schema, and conditionally adds strict validation, deferred loading, cache controls and fine-grained tool-input streaming. Strict eligibility depends on `tengu_tool_pear`, `tool.strict` and supported first-party/foundry model families; experimental betas can strip fields. The builder `xN_` selects available deferred tools, normalizes history and appends system sections. Model-specific beta headers come from `SJ8`; an eligible advisor model can append a *server-side* advisor tool only on agentic query sources when `GU()`, model support and advisor validity hold. Do not count that as an unconditional second local call, and do not infer its server-side cost from this binary [131602500-131604000; 131613955-131617000; 123621143].

**Model specialization versus business logic.** The visible specializations here are explicit model names and cutoffs in environment text, PDF support test excluding Claude 3 Haiku, strict-schema eligibility by Claude family, provider betas, and model capability gates for deferred tools and caching. Read-before-write, path permissions, search pagination, checkpointing and exit-code handling are executable policy, independent of model style. The inspected prompt builder does **not** demonstrate distinct task-policy recipes for GPT or Gemini. A Claude-specific statement in the environment prompt should not become a claim about the active non-Claude model [126697612; 123779678; 131602700; 129917200].

## Windows is a real tool dialect

**Observed.** On Windows, initialization looks for Git Bash from `CLAUDE_CODE_GIT_BASH_PATH` or a Git installation and can exit if missing. It skips executable candidates found inside the current workspace while resolving `git`. Path converters handle drive letters, UNC and `/cygdrive/` spellings [121035895-121037000]. `jGH` enables the separate PowerShell tool only when Windows *and* `CLAUDE_CODE_USE_POWERSHELL_TOOL` are set; a PowerShell implementation and output/progress type are present [123778110; 129604900-129607000]. That is not proof PowerShell is the default on this host. The Bash description continues to promise bash/zsh conventions, while PowerShell has distinct command parsing and permission logic. Drift should select one shell contract from detected executable, parser and workspace capabilities, and encode literal path quoting, current-directory handling, background jobs and shell-specific read-only rules in that tool's description and runtime. Do not assume a Unix pipeline is valid PowerShell or that a Git Bash drive path is a Win32 file path.

## File mutation, checkpoints and failure boundaries

**Observed.** Read caches normalized text, a rounded `mtimeMs` and the requested offset/limit. Edit requires the read record to exist and not be partial. Its `validateInput` compares file content to cached content **only when** `oQ(path)>timestamp`; Write validates `Math.floor(stat.mtimeMs)>timestamp` without content comparison. During `call`, both re-read and compare content only if the fresh timestamp exceeds the recorded timestamp, or the read record is missing. Edit's call uses `mB8` for the patch, `qt` to write with original encoding/line ending, and stores new read evidence afterward. Write rereads using `$t` and calls `qt` with LF, even on a CRLF source. `qt` calls `fPH`, which resolves a symlink target, writes and flushes a sibling temporary file, preserves existing permissions, then renames over the target. If that fails it removes the temp file and writes the destination directly. This gives an atomic *replacement on the successful rename path*, but not an atomic conflict check, and the fallback can partially overwrite the file. Both tools invoke `jo.beforeFileEdited` and `XKH` before mutation when checkpointing qualifies; failed history tracking logs and returns rather than aborting the edit [129054200-129057500; 129063100-129065700; 129908806-129912000; 121044857-121048300].

Checkpointing `Bz` defaults on for non-SDK use unless disabled in settings/environment, while SDK use needs explicit `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING`. `XKH` backs up the pre-edit file once per current snapshot and records tracked paths. `hEH` takes a subsequent message-linked snapshot of tracked files, including deletion state, and keeps a bounded snapshot list. The Bash/PowerShell execution paths inspected here do not call `XKH` before arbitrary shell-driven file changes, so native-tool history must not be advertised as complete workspace history. Checkpointing does not repair a write that races an outside editor or falls through to the direct-write path. This is file-history/revert support, not a transaction across shell commands, hooks or external writers [128821495-128823500; 129792000; 129606300].

**Inferred failure cases to test rather than claim fixed:** change content while preserving or decreasing rounded mtime; modify between call's read and `qt`; two sessions editing the same path; symlink target change; UNC path bypassing validation; UTF-16/CRLF full rewrite through Write; denied path after a hook edits tool input; checkpoint backup failure followed by successful mutation. A per-path lock within Drift handles Drift-vs-Drift writers. An outside editor still needs a fresh content/hash check and conflict report; a simple `rename` alone cannot supply a cross-process compare-and-swap. Preserve user changes on failure. See the [context report](claude-context.md#file-read-state-and-invalidation) for the read-cache reset at compaction and the [execution report](claude-execution.md#hook-and-permission-ordering) for post-hook validation risks.

## Output limits and where results go

**Observed.** Read's default maximum is 2,000 lines and the default text-read token cap nearby is 25,000, with configurable byte/token overrides; the displayed prompt can conditionally disclose its byte cap. Grep has an independent 20,000-character result cap and pagination; Glob reports its 100-result default cap. Bash and PowerShell have 30,000-character tool-result limits and can attach `persistedOutputPath`/`persistedOutputSize` when process output is large; code at the shell call path links or copies a process output file and truncates that saved copy to 64 MiB. The general result processor can also persist oversized *text-only* results and send a preview/path instead. These are different stages, so the existence of a shell file does not guarantee every lost line survives [125237428-125241781; 129073723; 129079594; 129788691-129793000; 129604900-129607000].

**Proposed.** Return typed `complete`, `truncated`, `nextCursor`, `revision`, `fullResultHandle` and actual byte/row counts for search/read/process tools. Persist full process output before projecting a preview, with TTL and workspace isolation; a subsequent Read of the handle should verify the file is still available. For Grep, pagination should have a stable snapshot or warn if files changed since the prior page. Avoid presenting "No files found" when a run was actually truncated or canceled.

## Skills, agent context and dynamic instructions

**Observed.** The Skill tool refuses unknown, disabled-for-model or non-prompt skills. Deny rules take precedence over allow rules; plain prompt skills with only basic metadata may auto-allow, while others ask permission. Inline invocation expands command messages and returns `newMessages`; its `contextModifier` can add allowed tool rules, change main-loop model and set effort for continuation. A skill with `context="fork"` uses a separate forked execution path. Thus skill invocation may be a cheap prompt insertion *or* a model job, and optional model/permission changes must remain visible in the turn record [128912731-128915800].

Skills with conditional `paths` remain dormant until touched paths match; `zhH` activates them. Read, Edit and Write inspect ancestor `.claude/skills` directories and trigger discovery; project-settings disabled/plugin-only policy skips loading. Some discovery uses `fhH(...).catch(...)` without awaiting it, so a newly found skill need not affect the exact request that discovered its directory. MCP instructions, output style, language, memory, tools and environment can also modify subsequent prompt material. Treat workspace memory and skill files as lower-trust, versioned inputs, and mark tool results as data regardless of tags they contain; the system text's reminder about trusted-looking tags is guidance, not a parser-enforced trust boundary [129048263-129050000; 129916832-129920500; 126682000-126698000].

The Agent tool can run foreground or async child work, with inherited or specialized tools, model, permissions and context. Forking skills and subagent summaries incur separate requests. `PS8` additionally invokes `OS8` to classify a completed subagent's handoff **only in auto permission mode when `OTK` accepts the transcript**. A blocked result adds a warning for the main agent; if classifier is unavailable it allows handoff with warning. This is a conditional security check, not universal proof of completed-task correctness [128791059-128796100; 128900000; 127105703]. The server-side advisor gate is separate from these client-visible child jobs.

## Verification and stopping

The normal system guidance tells the model to understand code before editing, keep scope tight and avoid brute-force retries. The tool layer backs up *some* of that guidance with read gates, ambiguous-replacement errors, path permission checks, schema parse and exit-code handling. It does not require a passing test suite before a final answer. Stop/SubagentStop hooks can block completion and feed feedback into another model turn; TaskCompleted/TeammateIdle checks can run conditionally afterward. There is also a three-attempt recovery for max-output-token errors in the loop. These are separate control paths, not evidence of a hidden always-on verifier [126685900-126697000; 129053076-129065700; 129660392-129664000; 129675100-129677850]. The observed `verification_agent` string in `xN_` classifies a query source for beta handling; it does not establish that every task gets a verification-agent call [131613955].

**Proposed stopping rule.** Track user acceptance criteria and actual test/build results, distinguish skipped from passed checks, block final success only on explicit user/project requirements or observed failures, and offer Stop hooks a bounded number of corrective turns with a visible reason. Do not add a model-based verifier to every trivial edit: it adds latency/cost and can overrule a real test with an ungrounded opinion. For complex edits, an opt-in reviewer can inspect a frozen diff and test log, not speculate from a summary.

## Drift-owned design and existing risk

The checked-out Drift still generates prompt defaults by reading upstream family templates (`scripts/build-extensions.ts:8-39`), replaces the beginning with a Drift identity by string substitution (`:11-19`), and applies the selected family only if the first system string starts with the exact original template (`engine/opencode/plugin/prompt-overrides.ts:14-24`). Selection is substring-based on the model API ID (`:37-45`). A template change can silently skip an override; a provider/model ID variation can choose an ill-fitting family. The anthropic identity fallback prepends text but does not remove all inherited OpenCode or Claude-specific claims (`:28-35`). In particular `engine/upstream/packages/opencode/src/session/prompt/anthropic.txt:1-12` still gives OpenCode feedback and documentation instructions beyond its first line. The generated GPT-6 `gpt-astra` variant has different behavioral policies from the older `default.txt`, including subagent constraints and verification cadence. Identity rewriting is not a prompt compiler.

**Proposed compiler.** Store Drift-owned typed sections with authority and provenance: product/system invariants, user/developer instructions, selected agent policy, workspace instructions, environment facts, provider/model capability recipe, enabled tool catalog and task-local context. Resolve explicit conflicts by authority *before* compression, never by blind concatenation. Render provider syntax for system/developer messages, tool schema limits, caching and media separately. Tool dialects should be generated from the **same** platform-specific contracts used by execution: PowerShell versus Bash, read result formatting, path normalization, deferred discovery, pagination and permissions. Use model recipes for communication style and capability-specific nudges, not cloned vendor identity or assumed reasoning habits. Pin a rendered prompt revision and tool-schema hashes per request so retries and postmortems can recover exactly what the model saw. Keep user constraints and security rules lossless when compressing; compress repeated examples and volatile tool prose after measuring instruction compliance. Do not stuff full skills, whole MCP catalogs or duplicated shell policies into every request.

**What to adopt first:** read/version evidence plus locked writes; true shell/tool descriptions on Windows; explicit truncation/retrieval handles; prompt recipe snapshots and authority tests. Add path-triggered skills, optional exploration agents and stop-review loops only with measured task-quality and request-cost gains. The existing [context](claude-context.md) and [execution](claude-execution.md) plans cover deferred schemas, cache stability, scheduler and recovery, so those are dependencies rather than discoveries repeated here.

## Tests that can falsify these claims

| Fixture | What to assert in Drift |
| --- | --- |
| Same-mtime external rewrite, two sessions editing, symlink retarget, or ACL/path normalization change | Detect conflicts visible at validation and fail before writing; serialize Drift writers; checkpoint and read evidence identify the same resolved file. Inject an outside write after validation to characterize the residual filesystem race rather than promising unsupported cross-process compare-and-swap. |
| Read only a page/range, then Edit or Write | Full-read requirement enforced, with a way to perform a bounded full read on a large file; no fiction that a Grep hit equals full read. |
| CRLF/UTF-16 file, exact replacement with typographic quotes and two matching occurrences | Encoding/line endings preserved for edit; ambiguous replacements rejected; full rewrite explicitly declares normalization and produces a reviewable diff. |
| Windows drive/UNC/space-containing path through Read, Bash, PowerShell and permission checks | Shell-specific quoting and path mapping agree with file tools; no accidental Bash fallback or wrong read-only classifier. |
| 101 matching glob paths, 251 grep results, multi-megabyte process output, then persisted handle expiry | Pagination/truncation visible; retrieval accurate while valid; expiration reported, never silently rendered as empty success. |
| Model family changes during a session, skill directory appears after a read, lower-trust file contains a fake system tag | New request has the correct recipe and schema revision; dynamic skills appear at a documented boundary; file text cannot acquire higher authority. |
| Agent handoff in ordinary versus auto mode, Stop hook blocks repeatedly, no available verifier | Only eligible paths pay classifier/verifier cost; bounded corrective turns end visibly; test results remain authoritative. |

Static inspection establishes branch structure, not observed quality or latency. Measure foreground and hidden calls, input/cache/output tokens, prompt revision, truncated-result retrieval, wall-clock time and acceptance-test outcomes on the same fixture before treating any copied behavior as an improvement.
