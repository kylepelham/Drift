# Evaluating a Drift-owned engine

Research date: 2026-09-29. This is an executable-in-future evaluation design, not a benchmark of Claude Code against Drift. No authenticated model call was made. The inspected Claude executable is `C:\Users\KylePelham\.local\bin\claude.exe`, version 2.1.85; its hash and inspection limits are in [the binary comparison](../claude-code-binary-comparison.md). Byte offsets below refer only to that exact binary. No implementation change is proposed as already validated.

## Decision to make

Would a smaller Drift-owned engine deliver better completed coding tasks and lower time to useful output than the current bundled OpenCode engine, without losing provider behavior or recovery guarantees? Keep the bundled engine as a candidate, not a straw man. Evaluate changes one at a time against it before treating a rewrite as a product direction. Model-specific behavior can be valuable, but provider conformance and recoverable execution must not depend on one model's happy path.

The earlier report's local tool ranking, cache-stable discovery, scheduling, and context attribution findings are hypotheses about benefits, not measured wins. A schema search still requires a model tool turn. Routing off, Jev routing, direct MCP, code mode, and native opt-in LLM are different baselines. An owned engine could remove work, or it could lose OpenCode's accumulated provider fixes, retry handling, tool-call normalization, and cost accounting. The provider cost is especially concrete: `engine/upstream/packages/opencode/src/session/llm.ts:224-280,294-353` contains a native-runtime fallback to AI SDK, provider transform, tool-call repair, provider options, and telemetry; `session/session.ts:338-403` normalizes cached tokens, provider metadata, context tiers, and billing. Treat each provider/model/transport combination as a contract to port and test, not a generic adapter.

## Measurement contract

Use a monotonic host clock within each process and stable correlation IDs across process boundaries. Do not subtract clocks on different machines. For local runs, record event timestamps at both sender and receiver and treat clock alignment as an estimated offset; report raw per-process intervals if the offset is unknown. Define a turn as one admitted user input plus all provider attempts and tool steps until idle, abort, or terminal failure. Distinguish a provider attempt from a user turn and a tool call from its durable side effect.

| Timestamp | Meaning and owner |
| --- | --- |
| `ui_submit`, `engine_admit_start`, `engine_admit_commit`, `ack_received` | User intent, durable admission, and HTTP acknowledgment. A failed acknowledgment does not imply failed admission. |
| `prepare_start`, `prepare_end`, `request_start`, `request_bytes_sent` | Engine preparation and transport. Separate provider request setup from the actual write where measurable. |
| `headers_received`, `provider_first_event`, `provider_first_text_delta` | HTTP response, first parsed provider message, first nonempty text delta intended for the user. Preserve reasoning/tool deltas separately. |
| `engine_text_published`, `sse_bytes_received`, `store_text_applied`, `ui_first_visible_text_paint` | Publication, network, reducer, and browser paint. Mark visibility with `requestAnimationFrame` after DOM text exists and the view is actually visible; a hidden pane has no first-visible-token sample. |
| `tool_queued`, `tool_started`, `tool_effect_committed`, `tool_result_durable`, `tool_result_published`, `turn_terminal` | Waiting, effect, durable outcome, event, and terminal state. |

Report `TTFT_provider = provider_first_text_delta - request_bytes_sent`, `first_event = provider_first_event - request_bytes_sent`, `first_visible = ui_first_visible_text_paint - ui_submit`, and engine/UI segments independently. If text never arrives, report a censored observation and the reason; never silently drop it from p95. First useful artifact can be a tool result or patch, and is a separate, task-specific measure. Provider chunk boundaries and CLI stdout buffering are not equivalent to UI paint. Keep cold process launch, warm process, cold workspace, cold/warm provider connection, and cold/warm prompt cache as distinct strata. State exactly whether session history and tool catalog were preloaded.

One proposed NDJSON record per boundary, with secrets and raw prompts excluded by default:

```json
{"schema":1,"run":"r-17","pair":"p-04","variant":"baseline","task":"mcp-state-03","attempt":1,"turn":"t-1","span":"tool-2","parent":"t-1","event":"tool_effect_committed","clock":"engine-monotonic","t_ns":9812345000,"wall_utc":"2026-09-29T10:00:00Z","provider":"anthropic","model":"pinned-id","transport":"messages-stream","tool":"fixture.navigate","call_id":"c-9","effect_id":"e-9","fixture_seq":12,"status":"ok","usage":{"uncached_input":0,"cache_read":0,"cache_write":0,"output":0,"source":"fixture"}}
```

`run`, `pair`, `variant`, `task`, `turn`, `attempt`, `span`, and `parent` are required correlation fields; `clock` identifies the process clock domain. `call_id` is the model's tool-call ID, while `effect_id` is an idempotency key recorded by the fixture server before applying a mutation. Include engine build/commit, binary hash, provider API version, model snapshot, prompt hash, workspace snapshot hash, tools/schema hash, settings hash, seed and fixture version in a run manifest. Store redacted wire headers separately if debugging provider behavior. Usage must retain raw provider counters, normalized counters, cache TTL if known, pricing source, and missing/unknown values; zero is not a substitute for unknown. For a paired live run, capture Claude's result usage alongside host timing, without assuming its `duration_api_ms` and Drift's provider span share endpoints.

## Runner and fixtures

Start with a command-line controller outside either product: manifest loader, workspace copier, deterministic fake provider, deterministic MCP/HTTP tool server, fault proxy, event collector, verifier, and report generator. Keep one task's repo under a fresh temp root per run. The provider fixture replays ordered wire frames and validates the request contract (headers excluding secrets, tool schemas/order, cache controls, model options, message ordering, stop tokens and request IDs). It should also synthesize legal and malformed frames at fixed logical times. The tool fixture persists `effect_id`, before/after state and result digest to a small journal; tests can restart the runner or sever transport and then ask whether the effect occurred once, twice, or is unknown. A recorded real-provider response can help reproduce an issue, but cannot establish either engine's task quality; fixed text cannot adapt to different tool decisions.

Suggested fixture definition, versioned with the runner:

```json
{"id":"mcp-state-03","version":1,"repo":{"archive_sha256":"...","setup":["bun install --frozen-lockfile"],"test":["bun test"]},"prompt_file":"task.txt","model":{"provider":"fixture","id":"replay-v1","effort":"fixed"},"tools":{"catalog":"catalog-40.json","allowed":["fixture.navigate","fixture.read","fixture.write"],"locks":{"browser-session":"exclusive"}},"clock":{"kind":"virtual","seed":41},"provider":{"script":"streams/partial-tool-call.ndjson","expect":"wire/request-03.json"},"faults":[{"boundary":"after_tool_effect_before_result_commit","once":true,"action":"kill_engine"}],"oracle":{"checks":["state/effects.json","bun test"],"forbidden":["duplicate_effect","unauthorized_write"]},"limits":{"turn_ms":120000,"provider_calls":8,"cost_usd":0}}
```

The archive hash, setup command and oracle are fixture inputs, not recommendations to run untrusted setup on the host. Run in an isolated temp workspace with outbound network disabled for deterministic fixtures; pin tool schemas and expose a fixture clock. Before any live comparison, verify both CLIs can select identical model/version, effort, system instructions, tool availability, permissions, workspace snapshot, budget, and output visibility. If Claude cannot use the same provider/model or exposes hidden instructions that cannot be matched, label that comparison **product-level**, not an engine A/B. `--bare` versus a minimal Drift run is a separate experiment; ordinary product defaults are another. Do not interpret partial CLI stdout as an app-paint time.

## Test matrix

| Scenario | Controlled input and expected observation |
| --- | --- |
| Transport and provider conformance | Fake Anthropic-style and OpenAI-style streams: text, reasoning, fragmented UTF-8/JSON, tool-call deltas, multiple tool calls, malformed and unknown events, usage only in final chunk, cache fields, response headers, 429 with retry-after, 5xx, disconnect before/after first delta, empty completion. Assert normalized transcript, exact outbound options, billed counters, retries, no ghost completion. Run each supported provider/model/transport combination; unsupported features must reject explicitly rather than silently drop options. |
| Streaming fallback | Primary stream fails before any committed output, then after visible text. Characterize the old engine or deliberately violate the new dispatch barrier for an additional after-tool-effect case; that is not a permitted normal mutation path in the new design. Switch model only when policy permits. Assert explicit provisional-output invalidation, no repeated write, usage attribution and correct fallback context. Simulate duplicate chunks after reconnection. |
| Durable boundaries | Inject kill, abort, lost HTTP acknowledgment, SSE disconnect and restart before/after admission commit, provider request send, tool effect commit, tool result commit, and output publication. Assert one admitted prompt, honest unknown status when execution cannot be proven, replayed output without repeated side effects, and no automatic replay of ambiguous provider/tool calls. Client retry must carry the same admission key. |
| Cancellation | Stop before admission, during preparation, mid-stream, waiting on approval, during a slow read, after an irreversible write, and during fallback/retry sleep. Assert prompt status, abort propagation, no new tool starts after cancellation, and honest reporting of writes already committed. Measure time to quiescence, not only time to HTTP abort response. |
| Slow/stateful MCP | Catalogs of 5, 40, and 200 tools; slow schema discovery; two safe reads; browser navigation plus dependent read; competing writes across sessions; tool never returns; tool returns after cancellation. Assert allowed tool recall, schema correctness, isolation, serial order where required, safe-read overlap, wait time and error recovery. Annotation `readOnlyHint` is a hint; fixture policy is authoritative. |
| Context and cache | Conversation grows across repeated tool output, image/file input, compaction, pruning and resumed turn. Assert exact assembled request hashes and retained evidence, no fabricated summary, cache-control prefix stability, provider cache read/write/uncached counts, and cost under each TTL. Long context cases at 25%, 75%, and near effective model limit must include lost-in-the-middle retrieval and a late correction. A small prompt is a control. |
| Startup and UI | Cold executable to ready, cold workspace to first send, warm turn, background tab, remote SSE, one delta per chunk versus 128 in one chunk, hidden chat and switched workspace. Measure readiness detection, send-to-ack, first event, first text, first visible paint, p50/p95 and timeout share. Tag process creation, build hash, environment and cache state. |

Add coding tasks whose acceptance depends on reading the repository: a localized bug with hidden regression, cross-file feature with a documented interface, a migration with backward-compatibility checks, and a request that should ask for clarification rather than guess. Include permission-denied and unavailable-tool tasks so "more edits" is not rewarded. Quality oracle: clean-room test suite on the resulting tree, file/diff invariant checks, tool-effect journal, and blinded human review for ambiguous correctness and maintainability. Record partial success, regression, unsafe side effect, test modification, and refusal separately. Tests alone are insufficient if an agent weakens them. Keep task instructions identical and freeze starting commits; an agent may use different valid paths to the same outcome.

## Paired live evaluation

Before paying for model calls, freeze a manifest with at least 40 distinct tasks across the matrix, reserve at least 20 held-out tasks authored by people who did not build the proposed engine, and pre-register the primary outcome and exclusions. These are proposed starting sample sizes, not a power calculation. Run each task on both variants from fresh identical worktrees, alternate order within task, and repeat stochastic tasks at least three times per variant on separate randomized blocks. Report paired task-level differences and confidence intervals by bootstrapping **tasks** (not correlated retries), plus per-stratum counts and failures. For 40 tasks, a 5-point win is only about two extra tasks; treat it as inconclusive without a suitable interval and enough coverage. If a provider version, model, prompt, or tool catalog changes mid-run, restart or report a separate cohort. Do not optimize against held-out tasks; rotate in new tasks and retain regressions as permanent tests after disclosure.

Primary metric proposal: proportion of tasks passing the blinded acceptance oracle with no forbidden side effect, paired at fixed model/effort and a declared cost and time budget. Secondary: time to correct completed task, first visible token, p95 full-turn latency, provider attempts, tool errors, context retention, cache read/write/uncached tokens, provider-billed dollars, and amount of manual repair. Measure quality even when one variant times out; report censored time and failure category. Quality and latency are separate axes. A faster incorrect task is a loss.

Release gates proposed before implementation, not measured thresholds: no duplicate effects in fixtures whose tools implement idempotency receipts; no automatic retry of ambiguous mutations without such support; explicit `outcome_unknown` recovery; zero unauthorized writes; complete and ordered text/tool transcript for conformance fixtures; no unexplained usage discrepancy against known counters; no regression on retained-feature tests; and no statistically credible quality loss on held-out tasks. For a speed claim, require at least a 10% improvement in median first-visible time and non-worsening p95 full-turn time in the matched configuration, with task-bootstrap intervals reported. For a quality claim, pre-register a practically relevant margin such as 5 percentage points, then collect enough pairs to bound it; 40 tasks will rarely suffice. An effect-reconciliation failure blocks release until reproduced, explained and retested. This is not a universal exactly-once guarantee. Gates apply per provider. If live samples are unaffordable, ship only fixture-backed reliability claims and mark live quality and speed unknown.

## Next concrete step

Build the trace recorder and deterministic provider/tool fixtures before building a replacement engine. First run the fixtures against current OpenCode as a characterization baseline. This reveals where Drift's observable behavior differs from its assumed behavior and gives the owned engine a precise compatibility target. Preserve the fixture suite and held-out tasks independently of either engine implementation.
