# Provider contracts for a Drift-owned engine

Research snapshot: 2026-09-29. Design proposal, not an implementation or a claim of live account entitlement. Sources below are official public documentation read on that date, plus the checked-in upstream source. Context7 was consulted for provider and gateway/local APIs; the LM Studio lookup exhausted its Context7 quota, so its primary documentation was checked directly. Public docs and aliases change, so resolve actual model availability at connection time. No credential files or paid endpoints were consulted.

## Decision and boundaries

All four access modes are required: **direct API keys**, **ChatGPT/Claude subscription sign-in** (and SuperGrok where supported), **gateway accounts/keys** (including OpenRouter and OpenCode Zen), and **local models**. Drift owns model discovery, auth integration, transport, adapter, and turn orchestration for every mode, including the currently bundled Claude Pro/Max login plugin's behavior. No OpenCode plugins or upstream runtime are part of the replacement. Detailed login and credential mechanics belong in [native-auth.md](native-auth.md); this document specifies the generation-side route and replay contract. Implement Anthropic Messages, OpenAI Responses, and xAI Responses natively, plus endpoint-specific Chat Completions, gateway passthrough/translation and local server adapters as required by verified profiles. A shared HTTP client may implement framing, but it must not turn xAI, subscription backends, gateways or local servers into a fictitious OpenAI API. Keep access mode, service identity, endpoint, model capability snapshot, and account identity on every request and saved turn. Never exchange one mode's credential or response ID for another's. [A1][O1][X1][L1][L2][G1][G2]

This research covers generation, tool exchange, replay, caching, compaction, cancellation, errors, and authorization boundaries. UI, policy, tool execution, persistence migrations, and detailed auth flow implementation are separate design work. `src/engine/bench.ts:20-45` names Claude Sonnet 4.6; `src/i18n/en.ts:424` names Astra in prompt settings. Those are public repo hints, not evidence of linked accounts or subscribed models. The vendored Codex plugin exposes an allowlist including GPT-6 Sol/Luna, but that is code behavior, not an entitlement guarantee (`engine/upstream/packages/opencode/src/plugin/openai/codex.ts:12-16,288-325`).

## Lossless turn IR and adapter contract

The source of truth is an append-only, ordered provider exchange, not a flattened chat transcript. Proposed shape (illustrative schema, not code):

```text
Turn { id, sessionId, parentTurnId?, service, upstream?, routeId, endpoint, model,
       modelInstance?, accessMode, accountId?, capabilityRevision, requestId?, state, usage?, error?,
       continuation?, blocks: OrderedBlock[], events?: RawEventRef[] }
OrderedBlock { localId, ordinal, role?, kind, status, providerItemId?,
               providerBlockIndex?, callId?, parentItemId?, phase?,
               display?, replay: ProviderTaggedPayload?, raw: BlobRef?,
               text?, mediaRefs?, annotations?, provenance? }
Continuation = full_history | { service, routeId, accountId?, responseId, store: true }
             | { service: openai, routeId, socketId, streamId, responseId, store: false }
```

`kind` includes text, reasoning, redacted reasoning, tool call, tool output, hosted-tool activity, citation, tool discovery/reference, refusal, compaction, and unknown. `replay` is the service- and endpoint-native validated JSON block/item with unknown fields retained; `raw` is a restricted original payload reference when round-trip preservation requires it. Parsed text and unified UI events are projections, never used to regenerate signed or encrypted blocks. Preserve response ID separately from output item `id` and function `call_id`; preserve Anthropic message ID, block index, `tool_use.id`, `signature`, and exact block order. Opaque reasoning is never reconstructed from visible summaries. A signed block produced through a gateway is replayable through that same verified route only; a provider-native-looking block is not portable across gateway policies or account boundaries. Keep original attachments by content address and their wire metadata. Keep secrets and authorization headers out of the IR and event log. [A2][A3][O3][O4][X3]

On every stream: persist an immutable attempt marker before sending; collect deltas by provider index/item ID; expose provisional UI text with attempt/revision identity; commit replayable blocks and continuation cursor atomically only after terminal completion and validation. Preserve incomplete/failed/aborted output as audit state, not as replayable assistant history. Unknown events are retained with bounded storage and never mistaken for completion. Mutating or unknown tools require a committed complete call and validated arguments. Certified non-effectful reads may execute speculatively under the stricter rules in [the owned design](owned-engine-design.md#scheduling-policy); their results become replayable only if the completed response confirms the identical call. A local `(attempt, provider call id)` key deduplicates dispatch within that attempt, but supplies no remote idempotency guarantee. Persist resolved tool outcomes before the next model request. Never automatically rerun an ambiguous side effect after a crash or assume interrupted inference was not billed. Keep faithful same-route replay distinct from explicitly lossy export to an incompatible model, route or account; retain originals, record omissions and sever response-ID lineage. [A2][O3][X3]

Capability resolution is an explicit `(provider, endpoint, model snapshot, access mode, API version/beta headers)` profile with booleans/enums plus limits: input modalities, output modalities, reasoning modes/efforts/display, tool types and schema subset, deferred loading, parallel calls, caching mode/TTL, compaction mode, state retention, transport, and context/output limits. Prefer official Models API/catalog metadata where available, augment with reviewed overrides carrying source URL and revision; unknown means disabled or an explicit probe, never guess from `id.includes(...)`. Reject unsupported combinations at request construction with a precise diagnostic. A provider accepting an ignored parameter is not a successful capability probe. Snapshot chosen capabilities with the turn so replay semantics do not drift when an alias advances. Anthropic's current thinking table differs substantially across 4.5, 4.6, 4.7, 5, and 5.5; xAI's `reasoning.effort` on multi-agent models changes agent count rather than reasoning depth; OpenAI effort and mode availability also varies by model. [A4][O5][X4]

### Capability data and deterministic route selection

Use a versioned registry of **service routes**, **endpoint contracts**, **model instances**, and **verified feature evidence**, rather than a universal model map. This illustrative record is a schema proposal, not a claimed catalog response:

```json
{
  "profileId": "local-lmstudio/instance-42/responses/v1",
  "revision": 7,
  "access": { "mode": "local", "service": "lmstudio", "accountRef": null },
  "route": { "baseUrlRef": "configured-local-1234", "path": "/v1/responses",
    "wire": "lmstudio-responses", "authRef": null, "headers": {}, "apiVersion": "server-version" },
  "model": { "requestId": "example-model", "instanceId": "instance-42",
    "artifactDigest": null, "loaded": true, "context": { "configured": 4096, "maximum": 32768 },
    "outputLimit": null },
  "features": {
    "reasoning": { "mode": "display-text", "replay": "unverified" },
    "clientTools": { "mode": "unknown", "parallel": "unknown", "schema": "unknown" },
    "structuredOutput": "unknown", "hostedTools": [], "deferredTools": false,
    "continuation": "unknown", "cache": "unknown", "compaction": "client-only"
  },
  "evidence": [{ "feature": "route", "level": "documented", "url": "https://lmstudio.ai/docs/developer/openai-compat/responses", "observedAt": "2026-09-29" }]
}
```

Types: `wire` is a closed discriminator (`anthropic-messages`, `openai-responses`, `xai-responses`, `openai-chat`, `openrouter-messages`, `openrouter-responses`, `zen-messages`, `zen-responses`, `lmstudio-rest`, `lmstudio-responses`, `ollama-chat`, `ollama-responses`, or versioned `compatible-chat:<server>`). `accountRef` and `authRef` are opaque local references, never credentials. Each feature is `documented`, `observed`, `user-configured`, `unsupported`, or `unknown`, with evidence URL/date/server version and optional expiry. `documented` is only proof for the documented route and model set; `observed` requires an opt-in harmless probe or sanitized fixture, not mere HTTP acceptance. A compatible endpoint may omit fields or synthesize IDs; store the raw result and explicitly mark degraded replay. Split context into model maximum, configured loaded-instance window, and available input after output reserve, system/tools and safety margin. `outputLimit:null` is unknown, not unlimited. [G1][M1][M2]

Selection algorithm for each turn:

1. Resolve the user's **explicitly selected access profile and model**. Read only its non-secret catalog or local-server metadata; refresh on server restart, instance load/unload, alias/digest change, or capability TTL expiry. A provider slug inside a model name does not pick a transport.
2. Enumerate that profile's documented endpoints and runtime-available instances. For gateway fallback, compute the intersection of every permitted upstream endpoint's capabilities, or pin the routing target for nonportable reasoning and continuation. Do not merge a direct provider's feature list into a gateway route.
3. Match required features (modalities, local tools, reasoning replay, structured schema, context/output budget, privacy/state, hosted tools, transport) against route evidence. Unsupported fails with an actionable message; unknown is not silently enabled. If only optional features are missing, choose an explicit degraded profile and disclose which semantics are dropped.
4. Select the best **verified** endpoint in that access profile: native passthrough where it preserves signed/encrypted blocks, otherwise the service's native contract, then verified compatible chat. Never switch endpoint, account, region, model instance or upstream mid-lineage without a replay boundary. Bind headers and credentials to the exact trusted base URL and route; record a header-name allowlist and reject credential-bearing redirects to other origins.
5. Snapshot effective capability revision, upstream/instance identity, context budget, transport and lineage in the turn. On first response compare advertised versus actual shape and router metadata; a mismatch fails or downgrades subsequent turns, never retroactively claims preservation. On 4xx do not auto-retry through a different transport that loses history. [G1][G2][G3][M1][M2]

### Gateways and local models are first-class access profiles

**OpenRouter:** Its public API documents `/api/v1/messages`, `/api/v1/responses`, `/api/v1/chat/completions`, model metadata and per-endpoint routing. Treat OpenRouter Messages and Responses as **OpenRouter contracts**, even where the payload resembles Anthropic or OpenAI. Keep OpenRouter-specific routing metadata, error envelope, header names and IDs; only replay opaque provider reasoning/signatures after a round-trip fixture proves fidelity on that exact endpoint and routing policy. For a signed/encrypted conversation pin an upstream with no fallback and use a verified endpoint; otherwise choose a deliberately lossy compatible route with full manual history. Chat `provider.require_parameters:true` narrows providers supporting submitted parameters, but is not proof of end-to-end signed replay or server tool availability; default load balancing/fallback changes the upstream. `/models` metadata and endpoint-level limits seed candidate profiles, not final proof. OpenRouter response caching is a distinct gateway request cache, not the upstream prompt cache. [G1][G3][G4]

**Zen:** The current OpenCode Zen docs list per-model `/zen/v1/messages` for Claude and `/zen/v1/responses` for GPT, with separate IDs/entitlement and usage. Route each through a Zen-specific contract with its own model catalog, authorization, errors and replay fixtures; do not route by OpenCode SDK package name alone or treat Zen as an OpenAI-key backend. No blanket assumption that Zen forwards Anthropic beta headers, OpenAI ciphertext, deferred tools, or compaction. The checked-in app documents an anonymous `public` key for some free models but explicitly says it does not authorize Jev; account balance/Go-plan and tool-routing entitlements differ (`docs/engine.md:107-126`). [G2]

**Other gateways:** Support a configured service URL, credential binding and declared wire contract as a required mode, including known passthrough and compatibility profiles. Cloudflare's checked-in routing uses native OpenAI/Anthropic wrappers for those models and a distinct catalog-aware compatible route for other providers (`engine/upstream/packages/opencode/src/provider/provider.ts:875-931`); that implementation is evidence of route diversity, not a stable Drift contract. Gateway-scoped custom headers and beta/version headers must be allowlisted per destination. Disable hosted/deferred tools, provider compaction, remote state and provider prompt-cache controls until the gateway documents or verifies exact forwarding and output preservation. Expose gateway tools only when the gateway itself documents them. Account-controlled gateways and corporate reverse proxies can inject or remove headers, reroute models, transform errors and truncate SSE; profile these separately. [G1][G2]

**LM Studio:** Use its v1 `GET /api/v1/models` to discover artifact key, loaded instances, configured `context_length`, maximum model context, vision, tool training and reasoning options. The v0 model endpoint is legacy, not the default for a new implementation. Match a selected loaded instance, not only a downloaded filename; refresh if its context setting changes. Its documented `/v1/responses` supports streaming, local previous-response state and optional Remote MCP, but none of that implies OpenAI encrypted reasoning or hosted OpenAI tools. Prefer a versioned LM Studio REST or compat endpoint with dedicated parsing. Confirm tool-call schema, reasoning representation and JSON Schema adherence for the actual loaded model/runtime; model training metadata is a hint, not a successful tool-call probe. [M1][M3]

**Ollama:** Native `GET /api/tags` lists installed models, `/api/ps` loaded models and `/api/show` supplies model details/capabilities; inspect runtime context settings separately. Native `POST /api/chat` uses streamed JSON objects (not SSE) with `message.thinking`, optional `tool_calls`, `think`, and `format` for JSON/schema on supported models. Its OpenAI compatibility supports a **subset** of Chat and stateless Responses, not OpenAI stored continuation or provider-encrypted reasoning. Prefer native Ollama chat when native thinking/tool behavior is needed, use compatible Responses only for verified supported fields, and never generate an API key for an unauthenticated loopback service merely because an OpenAI SDK asks for one. Preserve local model digest/quantization, configured `num_ctx`, template/tool formatting and the actual terminal token counters. [M2][M4]

For arbitrary local OpenAI-compatible servers, discover `/v1/models` only if offered, allow a user-supplied context ceiling when the server reports none, and begin with manual-history text chat. Opt-in feature probes are reproducible, harmless and version-scoped: one schema-valid function/tool exchange, one structured-output validation, one reasoning replay, one streaming terminal event and one cancellation. A 200 response with a field ignored does not pass. When local context is uncertain, reserve output and compact before the conservative configured ceiling instead of claiming the upstream model's advertised maximum. Drift-owned tool search and compaction remain possible without provider-native deferred tools or compaction. [M1][M2][M4]

## Anthropic Messages adapter

Request: direct `/v1/messages`, `x-api-key` and `anthropic-version`, scoped beta headers only when profile allows. Supply `model`, `max_tokens`, separate `system`, ordered `messages`, `tools`, `tool_choice`, thinking and cache settings. `thinking: {type: "adaptive"}` and optional `display: "summarized"` are profile-gated; older models may require `enabled` plus `budget_tokens` (minimum 1,024 and normally less than `max_tokens`). Current thinking can be omitted by default even when enabled, while signed empty text remains meaningful. For Claude 4.7+ manual `enabled` is rejected; manual interleaving beta is not interchangeable with adaptive interleaving. Do not force a legacy beta header on every model. [A1][A4][A5]

Decode `message_start`, `content_block_start`, indexed `content_block_delta` (`text_delta`, `input_json_delta`, `thinking_delta`, `signature_delta`), `content_block_stop`, `message_delta`, `message_stop`, `ping`, and in-stream `error`. Accumulate partial tool JSON until block end, keep signed thinking blocks including empty/omitted text and `redacted_thinking` as returned, then replay the assistant content array unchanged followed by user `tool_result` blocks referencing each `tool_use.id`. `stop_reason=tool_use` schedules client tools; `end_turn`, `max_tokens`, refusal, pause, and compaction are distinct terminal outcomes. Streaming usage on `message_delta` is cumulative, not incrementally additive; record `input_tokens`, `output_tokens`, cache creation/read, and thinking details when supplied. Preserve server-tool output and citations as server-executed content, never execute those tool names locally. [A2][A3][A6]

For large tool catalogs, gate `tool_search_tool_regex_20251119` or `_bm25_20251119` by profile; mark deferred client tools `defer_loading: true` while retaining at least one non-deferred tool. Search output carries `tool_reference` blocks that the server expands; keep these ordered blocks for replay and audit, not as local tool results. Tool lists, order, system text, thinking settings, and cache breakpoints affect prompt prefixes. Use either top-level automatic `cache_control` or explicitly placed cacheable blocks according to the model profile; record 5m/1h selection and actual read/write counters. Changing manual budget or thinking mode can invalidate breakpoints; never equate cache routing with guaranteed hits. [A5][A7]

Compaction has three separate paths: Drift-generated summaries, Anthropic on-demand beta, and threshold/context-editing beta. On-demand `compact-2026-09-04` returns a signed `compaction` block and `stop_reason=compaction`, not a user answer; persist the original history for audit, replace only the future replay window with the returned block first, carry its beta header on subsequent requests, and do not compact while client tool results are outstanding. The model and `system`/`tools` must match when retaining signed thinking across a compaction boundary. Check the Models API `capabilities.compaction` before enabling. [A8]

Error policy: parse HTTP typed errors and `request-id`, honor `retry-after` and rate-limit headers, distinguish spend-limit 429 (no retry-after), 529 overload, 5xx, auth/permission, invalid requests, and SSE errors after HTTP 200. Back off only before observable output or when safe to restart; if a stream has yielded calls/text, record an ambiguous attempt and require a deliberate continuation strategy. Abort the fetch/reader, cancel pending local work using the turn abort signal, and leave partial blocks non-replayable. [A3][A9]

## OpenAI adapter

For direct OpenAI API access, default to `/v1/responses` for eligible models. Encode `input` as ordered typed items, not concatenated role text. Preserve `response.id`, output item `id`, `output_index`, content index, `call_id`, message `phase`, reasoning `encrypted_content`/summary, annotations and tool-specific output. For `store: false`, replay **all** response output items in order plus new input; do not assume a summary is the reasoning state. For stored continuation, send `previous_response_id` plus only new items, and explicitly resend current instructions/tools as required by the API contract; do not mix a full-history replay with server continuation or silently reuse a response ID from another account/model/profile. Return to full history if stored state is gone and replayable items exist. Status `incomplete` with `incomplete_details.reason=max_output_tokens` is not a successful final answer, even if visible text is empty after billed reasoning. [O1][O3][O4][O5]

Tool definitions in Responses are `type:function`, top-level `name`, `parameters`, optional `strict`; calls appear as `function_call` items and results as `function_call_output` with the exact `call_id`. Validate strict JSON Schema locally against the supported subset (`additionalProperties:false`, required fields, etc.) before opting into `strict:true`; reject/relax explicitly rather than silently rewriting schemas. `text.format` is a separate structured-final-output contract; Chat Completions uses `response_format` and differently shaped tool calls. Hosted search, file search, code interpreter, computer, MCP and tool search have distinct typed items and execution ownership; computer use needs a Drift-owned environment and action loop, not an automatic server-side mouse. `tool_search` plus deferred functions/namespaces/MCP yields `tool_search_call`/`tool_search_output` items and is documented only for GPT-5.4+; enable by profile. [O1][O2][O6][O7]

HTTP SSE parser keys typed response/item/content events to IDs and indexes, collects argument deltas before dispatch, and distinguishes `response.completed`, `response.failed`, `response.incomplete`, and stream `error`. WebSocket `/v1/responses` is a separate transport profile: `response.create` and `stream_id` multiplex independent lanes; active-socket cached `previous_response_id` works with `store:false` but disappears across reconnect or eviction. On `previous_response_not_found`, rebuild from full replayable history, do not blindly resend only incremental tool output. Warmup `generate:false`, steering, and server compaction need their own state transitions and are not assumed by the HTTP profile. Abort must close/cancel the specific request/lane without contaminating other streams; test exact cancellation behavior before promising interruption. [O3][O8]

Prompt caching is model dependent: GPT-5.6+ supports explicit `prompt_cache_options.mode` and `prompt_cache_breakpoint` on supported content, 30m TTL; earlier models use implicit breakpoints and `prompt_cache_retention` where available. Tool definitions, formatting and reasoning configuration may change the rendered prefix. Track actual `usage.input_tokens_details.cached_tokens`, write accounting and model-specific prices rather than equating `prompt_cache_key` with a hit. Compaction via `/responses/compact` returns a new input window, not a response ID; `context_management` acts during generation when supported. Both terminate the old replay prefix intentionally; persist the before/after boundary. [O9][O8]

OpenAI API-key access to `api.openai.com/v1/responses` is separate from the **required** ChatGPT/Codex subscription access. The checked-in plugin routes subscription OAuth calls to `chatgpt.com/backend-api/codex/responses`, injects an account header and refreshes tokens and filters models (`engine/upstream/packages/opencode/src/plugin/openai/codex.ts:273-325,328-435`). That internal backend and its terms, fields, WebSocket behavior, rate limits, supported models and access policy cannot be inferred from the public OpenAI API reference. Own its route and credentials in Drift, with a separate **implementation-evidenced, not publicly documented** wire profile, captured contract fixtures and support/entitlement verification before enabling capabilities. Never plug the subscription token into the public API adapter. Detailed OAuth mechanics are covered in [native-auth.md](native-auth.md). [L1]

## xAI adapter

For direct xAI API-key access prefer its documented `/v1/responses` using `XAI_API_KEY`; implement its own encoder, decoder and feature allowlist. It supports `previous_response_id` on stored responses (normally 30 days) and `store:false` with full local replay and `include:["reasoning.encrypted_content"]` on eligible models. Grok 4.7 returns encrypted content by default on Responses; retain reasoning items and tool ciphertext unchanged along with server tool output. Chat Completions does not expose that ciphertext. Never substitute a plain visible reasoning summary for it. `instructions` cannot be combined with `previous_response_id` per the xAI reference; the prior prompt is used, so change instructions only with a new full-history lineage. xAI accepts some OpenAI fields only for compatibility without executing them: specifically do not claim OpenAI background, metadata, truncation, or server compaction support. [X1][X2][X3]

Stream typed SSE events with xAI-specific validation, preserving response/item IDs, status, reasoning summary events, citations, and server-side tool records. The function-calling guide says a streaming function call arrives whole in a single chunk; still parse by item identity and tolerate later contract changes. Custom calls use `function_call_output` by `call_id`; parallel calls are on by default and can be disabled with `parallel_tool_calls:false`, so return results for **all** calls before the next turn. Built-in `web_search`, `x_search`, `code_interpreter`, collections and image tools run server-side; distinguish their cost and results from local tool dispatch. Current public tool overview does not document a native xAI computer-use tool: do not advertise one; a Drift-provided UI function is a separate client tool. xAI's Responses reference says only functions and web search are supported in one `tools` description while its tools overview demonstrates more, so gate each hosted tool by a verified model/endpoint profile and record the documentation discrepancy. [X2][X5][X6]

Use Responses `prompt_cache_key` or Chat `x-grok-conv-id` for sticky routing, but preserve exact prior message/response prefix including encrypted reasoning; changed/reordered history causes misses. Record `usage.input_tokens_details.cached_tokens`, `output_tokens_details.reasoning_tokens`, server-tool counts, source counts, and xAI's cost fields when returned. On reasoning models avoid `presencePenalty`, `frequencyPenalty`, and `stop`; Grok 4.5 and 4.6/4.7 expose different effort ranges and Grok 4.20 multi-agent uses effort for agent count. Chat Completions has its own message and reasoning replay contract, and cannot deliver Responses ciphertext. xAI's Python SDK uses gRPC, another independent transport profile rather than an interchangeable REST implementation. [X1][X3][X4][X7]

Treat 401/403, model-access errors, 429, timeout, and 5xx by typed HTTP status and body; honor `retry-after` if supplied, add jitter/backoff only for safe attempts and preserve response/request IDs and partial outputs. Do not assume OpenAI error-code names or retry semantics on xAI. Abort fetch/SSE and prevent retries after cancellation. The vendored xAI plugin implements a SuperGrok device OAuth flow and injects a bearer into xAI-bound requests (`engine/upstream/packages/opencode/src/plugin/xai.ts:205-295,297-325`); own this required mode in Drift with its own account-scoped route and conformance fixtures. That code is **not** public documentation that a SuperGrok account authorizes every API feature or endpoint; verify entitlement and wire support per feature. Detailed auth mechanics belong in [native-auth.md](native-auth.md). [L2]

Claude Pro/Max sign-in is likewise required and Drift-owned: `docs/extensibility.md:5-13` documents the current bundled `@ex-machina/opencode-anthropic-auth@1.8.5` dependency and its model-access marker. Replace its integration in Drift rather than retaining the plugin or assuming an API key represents a subscription. Anthropic public Messages documentation establishes the **API-key** contract, not the subscription endpoint's accepted headers, beta features, signatures or spending model. Until the dedicated auth research verifies the subscription wire behavior, keep this a separate, implementation-evidenced access route whose capabilities require account/endpoint fixtures; do not simply graft subscription auth onto the public Messages profile. [L3][A1]

## Conformance plan before shipping any adapter

Version each sanitized fixture by `(provider, endpoint, model snapshot, access mode, API version, feature set)` and retain both wire frames and expected IR/re-encoded replay JSON. Synthetic fixtures are free and cannot prove a model or subscription entitlement. Public examples can seed fixtures; real captured fixtures require explicit authorization, redaction and no committed tokens or private content.

Acceptance gate: deterministic decode -> IR -> same-route encode preserves replay-relevant fields byte-for-byte where opaque or signed, structurally equivalent elsewhere; cancel/retry/state-lineage tests pass; capability matrix is validated against each documented model snapshot and **all required access modes**. Signed/encrypted same-provider replay through a gateway must prove exact route fidelity or be disabled. An opt-in live contract suite for accounts and local servers is a release requirement, with no unapproved paid calls; none was run for this document.

## Existing engine evidence and migration traps

- The vendored provider loader already selects `sdk.responses(modelID)` for both OpenAI and xAI (`engine/upstream/packages/opencode/src/provider/provider.ts:243-265`), but that only chooses SDK surfaces, not identical wire semantics.
- The current native runtime gates OpenAI/Anthropic/opencode models, excludes xAI and most OAuth, and lowers AI SDK-shaped `ModelMessage` into another native request (`engine/upstream/packages/opencode/src/session/llm/native-runtime.ts:46-71,74-103`; `native-request.ts:80-115,153-178`). A new Drift engine should not inherit this normalization as its durable format.
- Anthropic transform filters empty content and checks signed/redacted reasoning (`engine/upstream/packages/opencode/src/provider/transform.ts:168-195`); the session projection even inserts a single-space separator for some signed blocks (`engine/upstream/packages/opencode/src/session/message-v2.ts:266-288`). This is evidence of replay fragility, not a behavior to copy into a new lossless IR.
- Existing caching places provider-specific options on selected system/recent messages (`engine/upstream/packages/opencode/src/provider/transform.ts:358-383`). Native contracts need their own cache planning and invalidation.
- The current request path sets `strict:false` across OpenAI-family tools (`engine/upstream/packages/opencode/src/session/llm/request.ts:148-158`). Drift should choose strictness per validated schema and model profile.
- The vendored session projection turns same-model reasoning into AI SDK metadata but turns different-model reasoning into text (`engine/upstream/packages/opencode/src/session/message-v2.ts:366-379`). Never use that projection for signed/encrypted same-provider replay or claim cross-provider reasoning preservation.
- The current engine mixes OpenRouter, Zen, native passthrough and compatibility gateways in provider loading (`engine/upstream/packages/opencode/src/provider/provider.ts:159-166,502-521,875-931`), including model-ID route checks. The owned engine needs explicit route profiles and independent capability evidence, not copies of those routing heuristics.
- The shipped Claude auth plugin is downloaded on demand (`docs/extensibility.md:5-13`); replacing it is part of owning the subscription mode. `docs/research/opencode-exit-inventory.md:92` separately records the plugin exit constraint.
